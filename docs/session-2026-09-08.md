# Vellar Development Session, September 8, 2026

## Overview

This session closed the single most load-bearing conformance gap in the SCF
submission and shipped the feature the RFP weights highest. **C1 moved from
blocked to satisfied on testnet**: the x402-foundation e2e suite was run against
the live facilitator for the first time, settling six real payments verified
against Horizon. **Hybrid semantic search shipped**, pairing the existing lexical
ranking with Voyage AI embeddings fused by RRF, measured rather than asserted.
Alongside that, the demo corpus tripled, dependency alerts fell from 22 to 6,
two real bugs were fixed, two upstream PRs were filed, and **seven stale
documentation claims were found and corrected**, four of which understated the
project. Everything below names how to verify it.

### A note on scope

29 commits landed on `vellar-facilitator` today. The other repositories in the
org were not touched today: their most recent work (`vellar-dapp` dependency
bumps, `vellar-explorer` tests and CI, `vellar-playground` licence) is dated
**2026-09-07**, and `vellar-sdk`'s only commit today is `bc12014`. This log is
therefore mostly a facilitator record, and says so rather than absorbing
yesterday's work into today's total.

### Semantic search

Hybrid search shipped as PR #92 (`969a56c`). Lexical ranking was **not**
replaced, because it scores well on keyword-shaped queries and replacing it
would have regressed them.

- Voyage AI `voyage-code-3`, 1024 dimensions, one embedding per catalog entry
- Reciprocal Rank Fusion over the lexical and vector rankings
- **19 of 19 production entries embedded** in the Turso database
- `search()` stays synchronous behind in-memory caches, so a Voyage outage
  degrades ranking rather than hanging the endpoint

| Query set | Metric | Lexical | Hybrid |
|---|---|---|---|
| Original 10 | MRR | 0.950 | 0.950 (unchanged) |
| Original 10 | NDCG@3 | 0.963 | 0.963 (unchanged) |
| Semantic 10 | MRR | 0.264 | **0.717** |
| Semantic 10 | NDCG@3 | 0.263 | **0.789** |

Verify live:
`curl -s "https://vellar-facilitator.onrender.com/discovery/search?query=barcode+for+a+link&limit=3"`
returns `/qr` first, on a query sharing no token with that listing.

**Corpus expansion (PR #91).** The eval was measured against 8 entries in two
semantic clusters, which cannot produce a meaningful retrieval metric. Eleven
routes were added to the demo seller: `/qr`, `/color`, `/markdown`, `/diff`,
`/regex`, `/lorem`, `/csv`, `/password`, `/cron`, `/units`, `/weather`. The
catalog went from 8 entries in 2 domains to **19 across 12**. All eleven were
settled on-chain to enter the catalog.

**Still not claimed as met.** Five of ten semantic queries reach the top 3 but
not first place, and the corpus is one seller's demo. That is a reranking
problem, not a retrieval one.

### Security and dependencies

Dependabot alerts fell from **22 to 6**, verified against the GitHub API.

- `fast-uri` overridden to 3.1.7 / 4.1.4, closing four high-severity
  SSRF/host-confusion advisories. Overrides are **scoped per consumer** so each
  stays within its own major rather than forcing a cross-major jump.
- `qs` overridden to 6.16.0, closing two moderate advisories
- Same fixes applied to `examples/`

**`fastify` was deliberately held at 5.11.0.** Version 5.12.x changes hop-count
`trustProxy` resolution: with `trustProxy: 1`, `req.ip` returns the proxy
address rather than the forwarded client, so every client behind Render's proxy
would share one rate-limit bucket, reopening the D4 finding that
`src/hardening.test.ts` guards. Measured, not inferred:

| fastify | client A | client B |
|---|---|---|
| 5.11.0 | `203.0.113.1` | `203.0.113.9` (partitioned) |
| 5.12.3 | `10.0.0.1` | `10.0.0.1` (shared bucket) |

`trustProxy: true` is not the fix either; it takes the attacker-controlled
leftmost XFF entry. Tracked as issue #87. The failing test was not modified or
skipped, because it caught a real regression.

The two Rust contract advisories were **deferred**: rebuilding
`contracts/upto-stellar` would invalidate the reproducible-build hash published
in `docs/upto-deployment.md` and verified against the deployed contract, which
is a worse trade than a LOW and a MEDIUM.

### Bug fixes

**`server.ts:993`** (`f1d078b`), the trust resolver used
`https://soroban-testnet.stellar.org` as its RPC fallback **regardless of
`config.network`**. On pubnet with `STELLAR_RPC_URL` unset, it would have
queried testnet RPC while the facilitator settled on pubnet, and failed silently
because trust verdicts degrade to `unknown` rather than erroring. Three other
call sites in the same codebase branch on `config.network` correctly; this one
did not.

**`server.ts:961`** (`bb69714`), a hardcoded testnet passphrase string replaced
with `Networks.TESTNET`. An external review claimed this meant "every pubnet
payload would 400 before reaching the scheme". **That claim was wrong**, and was
disproven empirically: `TransactionBuilder.fromXDR` does not validate the
passphrase, and a pubnet envelope parses fine with the testnet value. The change
is cosmetic. The review was pointing at the right *class* of bug, and the real
instance was 32 lines below in the same function.

**`PROVENANCE.md`** (`0d62539`), a full diff audit against rail402 at pinned
commit `ff504b85` confirmed **zero local changes**: all four vendored files are
byte-identical, `src/lib.rs` sha256 matching upstream exactly. A note was added
explaining the three untracked paths a naive `diff -ru` would flag.

**`demo.sh` is broken** and has been since `6f5de85` (2026-08-31). It starts the
facilitator without `CHANNEL_ACCOUNT_SECRET_KEYS`, which `config.ts:414` has
required since the channel-pool PR, so the facilitator exits at boot and the
script reports a misleading "seller did not come up". Filed as issue #90. The
time-to-first-settlement measurement was taken via the hosted path instead.

### Catalog

Ten `localhost` entries, artifacts of test runs including this session's own e2e
run, were removed from the production Turso database after a full backup. The
`entry` table went 18 → 8 and `ownership` 21 → 11. Every deleted ownership row
had `verified_at NULL`, so no verified binding was touched.

A **probe-protocol gap** was found and documented as issue #89: Layer 2
ownership verification sends a bare GET, so input-taking routes answer `400` and
can never be verified. An attempted fix worked for verification but created an
on-chain loss path, observed rather than predicted: three settlements paid and
returned `handler_failed` with no result and no refund. **It was reverted**
(`96f06fe`), and the honest consequence is recorded: 5 of 19 entries verify,
9 are blocked by the probe protocol, 1 is an unfetchable route template.
